Xpert CSMS - how to run
=====================

Requirements
------------
- Visual Studio 2022 with the "ASP.NET and web development" workload and the .NET 6 SDK/runtime
- SQL Server (Express is fine)

1. Database
-----------
Option A - use the supplied data (CSMS.bak)
   CSMS.bak was taken on SQL Server 2022 (version 16). SQL Server can only restore a backup on the
   same or a newer version, so this needs SQL Server 2022 or later.
   SSMS > Databases > Restore Database > Device > CSMS.bak > restore as "CSMS".
   Nothing else to do: the migrations are already recorded in that database.

Option B - start with an empty database (also the way to go on SQL Server 2019)
   Do nothing. On first start the application creates the "CSMS" database and all tables by itself
   and, because the database has no users yet, creates a first administrator:
        user name: admin        password: Admin@12345
   (values come from "SeedAdmin" in appsettings.Development.json; change the password after signing in).
   That administrator can then create brokerage houses and branches, which registration needs.

2. Connection string
--------------------
XFLCSMS/appsettings.json > ConnectionStrings > DefaultConnection
   default:  Server=.\SQLEXPRESS;Database=CSMS;Trusted_Connection=True;...
   - "."            = this computer
   - "\SQLEXPRESS"  = instance name. For a default (unnamed) SQL Server instance use  Server=.
(The connection string is no longer hard-coded in Data/DataContext.cs.)

3. Run
------
Open XFLCSMS.sln and press F5 (profile "XFLCSMS" -> https://localhost:7044 or http://localhost:5100).
Do NOT run Add-Migration: the model and the migrations are in sync. Update-Database is not needed either
(the application applies pending migrations at start-up; set "Database": { "AutoMigrate": false } in
appsettings.json to switch that off).

4. E-mail
---------
Registration, "forgot password" and the e-mail notifications use the mail server entered in the application:
sign in as platform admin > System > Notification settings > E-mail server (password stored encrypted in the
database; "Send test e-mail" shows at once whether it works). While nothing is entered there, EmailHost /
EmailUsername / EmailPassword of appsettings.json are used (Gmail SMTP, port 587). If the mail cannot be sent
the user sees a message instead of an error page.
The system also works without e-mail:
   - a registration whose mail failed is kept as "Not verified"; the administrator activates it under
     Users (the menu shows how many accounts wait);
   - the administrator can create an account himself (Users > New user; active at once);
   - the administrator can set a new password for a user (Users > Edit).

5. Interface
------------
The pages no longer use AdminLTE, Bootstrap, jQuery or any CDN: everything is in wwwroot (css/app.css,
js/app.js, js/charts.js, fonts, img/icons.svg, img/xpert-logo.png), so the application also runs on a network
without internet access. The charts are drawn by js/charts.js, without a chart library.
Colours and fonts are variables at the top of css/app.css. Pages shared by all roles are in Views/Shared.

6. Letting other people use it (brokerage houses, colleagues)
-------------------------------------------------------------
"dotnet run" / F5 answers on localhost only: nobody else can open it. For other computers:

a) Same office network
   1. Start it with the "lan" profile (plain http on port 5100, all network cards, Production mode):
          dotnet run --launch-profile lan
   2. Allow the port in Windows Firewall, once, in a terminal opened "as administrator":
          netsh advfirewall firewall add rule name="XFL CSMS" dir=in action=allow protocol=TCP localport=5100
   3. Find the address of this computer:   ipconfig   (IPv4 Address, for example 192.168.1.25)
   4. The others open   http://192.168.1.25:5100
   The first start on an EMPTY database must be the normal profile (F5 / plain "dotnet run"): only that one
   reads appsettings.Development.json and creates the first administrator.
   Plain http means passwords cross the network unencrypted. Fine inside one office, not beyond it.

b) Brokerage houses outside the office (the real use)
   Needs a server they can reach and https: publish the project (dotnet publish -c Release), host it in IIS
   (ASP.NET Core Hosting Bundle) or as a Windows service behind a reverse proxy, with a certificate and a
   DNS name, and set ASPNETCORE_ENVIRONMENT=Production. The application itself needs no change for this.

Before a brokerage house can start, the administrator needs: the house (Brokerage houses > New), at least
one branch for it (the list flags a house without one), and then either the staff register themselves or
the administrator creates their accounts.

7. First steps after updating to version 3.0
--------------------------------------------
Start the application once: it adds its new tables by itself (nothing existing is changed) and brings the
status of old tickets in line with the eight statuses. Then, signed in as platform admin:
   a) System > Notification settings
        - "Address of this site": check it and press Save. Until it is saved, e-mails carry no link.
        - E-mail server: enter host, user, password, sender; "Send test e-mail".
        - SMS gateway (optional): address and fields of your SMS provider, then switch SMS on.
        - The table decides which event is reported through which channel.
   b) System > Roles & permissions: what each of the five roles may do. The defaults are sensible.
   c) Users > Edit: give one person of each brokerage house the role "House admin". He then manages the
      people and branches of that house himself.
   d) System > Demo data > Load demo data: houses, people of every role and 64 tickets in every status, to
      try everything. The page shows the accounts and their password. Best on a test database: the demo
      manager and engineers are working accounts. "Remove demo data" takes it away again.

The folder XFLCSMS/App_Data/keys is created at the first start. It holds the keys for sign-in cookies and
for the stored mail password / SMS key. The account the site runs under must be able to write there. Do not
commit it and do not let a deployment delete it. After a move to another server: enter the mail password and
the SMS key again (the settings page says when that is needed).

Run ONE instance of the application: the messages that appear on open pages are passed on inside the process.

8. First steps after updating to version 3.1
--------------------------------------------
Start the application once. It adds the table "Products" and a column "ProductId" to the support lists and
the tickets (nothing existing is changed), and - once, when there is no product yet - five starting products
with their support types and categories.
   a) Administration > Products: rename the starting products to the real product names of XFL, delete what
      does not apply, add what is missing. Only "Xpert Trading OMS" is a real name; the others are a start.
      Open a product to change its support types and categories.
      To start without the starting list, set  "Products": { "Seed": false }  in appsettings.json BEFORE the
      first start with this version.
   b) The support types and categories that existed before are kept as "All products": they are offered
      whatever the product. Edit one and choose a product to make it belong to that product only.
   c) Dashboard > Customize: every person arranges the own dashboard; nothing to set up.
The old logo file XFLCSMS/wwwroot/img/XFLlogo.png is not used any more and can be deleted.
If a page looks unstyled right after the update, reload it once with Ctrl+F5 (the browser kept the old files).

See WORKFLOWS.md for what each role can do, and FIXES.md for the list of what was changed.
